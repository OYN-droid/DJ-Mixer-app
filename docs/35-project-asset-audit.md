# Project asset handling audit

Date: 2026-07-18  Branch: `feature/project-asset-manager`  Scope: observed Phase 5A.2 implementation before Asset Manager changes

This audit records current code behavior. It is not a promise that every listed asset is durable or manageable. `DeckForgeProjectAssets` in `src/project-assets.js` is the existing authoritative project asset index from ADR-004. Audio bytes remain owned by their existing runtime or backend domain; the index stores JSON-safe metadata only.

## Existing asset registry contract

- Storage: `deckforge-project-assets:v1:{projectId}` in `localStorage`.
- Current fields: `assetId`, `projectId`, `owningDomain`, `createdBy`, `assetType`, `shared`, `references`, `checksum`, `missing`, `relinkRequired`, `sourceId`, `name`, `metadata`, `createdAt`, and `updatedAt`.
- Registration requires the active Project Registry session to own the supplied project ID. A matching `assetId`, or matching `sourceId` plus `owningDomain`, updates an existing record.
- Generated assets default to private. The current `shared` flag has no promotion, cross-project reference, or deletion-protection workflow.
- `list` and `remove` are project-scoped. Removal deletes the index row immediately; there is no trash, reference validation, undo record, or active-job guard.
- `markMissing` toggles both `missing` and `relinkRequired` without validating a source.
- The model does not persist `File`, `Blob`, `AudioBuffer`, `AudioNode`, MediaRecorder, timers, or object URLs.

## Object URL and runtime ownership

There is no separate cross-domain object URL service. Existing owners are:

- Recording service runtime map: creates one URL per completed Blob; revokes it on delete and service cleanup.
- Export service runtime map: creates/replaces one URL per completed output; revokes the previous URL, and revokes on delete and cleanup.
- One-shot downloads for Arrangement JSON/cue sheets, Beat Forge JSON, WAV/stem exports, DITC manifest, and Producer Memory create a URL and revoke it with a short timer.
- DITC, Decks, Pads, Stem decoded playback, Beat Forge, and Harmony Lab use `AudioBuffer`/Web Audio directly and do not require object URLs.

The Asset Manager must inspect these established owners through adapters. It must not persist or recreate runtime URLs and must not revoke a URL while its owner is previewing, finalizing, or downloading it.

## Backend and temporary files

- Stem uploads are copied to an operating-system temp directory. `stem_server.py` removes that directory in `finally` after processing, including cancellation/failure paths.
- Completed stems are copied to `generated_stems/{jobId}`. They remain until the completed job is explicitly deleted; server restart loses the in-memory `JOBS` entry, so orphaned output directories are possible.
- Recording chunks exist only in the Recording service runtime map until finalization; cancellation empties them.
- Export intermediate data and final Blobs exist only in the Export service runtime map. Current diagnostics report no filesystem temporary files.
- Arrangement, Beat Forge, DITC manifest, and memory downloads use short-lived browser Blob URLs and leave no managed file in the project.

## Current risk ledger

1. Local DITC asset availability becomes dishonest after reload because the browser `File` is gone while the asset row remains available.
2. Generated stems from different jobs can overwrite one logical registry row because common output IDs (`vocals`, `drums`, and similar) are not job-scoped.
3. Arrangement rows model clips as assets instead of modeling clips as references to their source assets; deletion/version changes do not reconcile the index.
4. Pads, Beat Forge, Harmony Lab, artwork, documents, and symbolic/render outputs are not consistently indexed.
5. Immediate asset removal does not check active jobs, shared ownership, Arrangement versions, saved pad banks, history/recovery, or Producer Memory.
6. `references` is an untyped string array. There is no authoritative active/historical usage graph or reference count.
7. The `shared` flag has no cross-project reference list or deletion protection.
8. Storage totals are unavailable or incomplete because most rows do not expose `sizeBytes`, and shared data cannot yet be counted once.
9. There is no trash, removal undo record, duplicate classification/resolution, manifest sanitizer, or reusable metadata-to-local link.
10. Stem backend files can outlive the in-memory job registry after server restart; the browser cannot safely enumerate or delete those orphans today.
11. Absolute/relative folder strings are descriptive only. No durable File System Access handle is stored, and reveal/consolidate actions are unsupported in the current browser architecture.

## Existing management controls

Project Library exposes project-level missing counts and validation but no asset list. DITC can remove its own runtime/file references, Arrangement can relink a selected missing clip, Stem Lab can remove a job after limited routing checks, and Recording/Export can delete their own outputs with URL cleanup. These controls do not share a usage graph or a safe-removal transaction. There is no current control for shared promotion, trash, consolidation, project-wide duplicate resolution, manifest export, or temporary cleanup.

This audit establishes the boundary for Phase 5A.3: extend `DeckForgeProjectAssets`, integrate existing domain owners, and disable actions that the browser or current backend cannot perform safely.
